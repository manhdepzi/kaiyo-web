# Business Rules Matrix — PROPOSED / UNAPPROVED

## 1. Status and use

**Document status: PROPOSED — UNAPPROVED.** The repository has no approved Product Requirements, role/permission matrix, state machines, or DB/API/Event contracts. The user authorized creation of a reviewable proposal on 2026-08-22; that authorization is not approval of the individual rules below.

These rules are precise enough to derive tests, but **must not be implemented** until each rule is accepted, changed, or rejected by an authorized product/architecture owner. Approval must also produce the corresponding database/API/event contracts before schema or public interfaces are created.

## 2. Reading the matrix

- Every row is `PROPOSED` unless an approval record later identifies the approver, decision date, and approved revision.
- “Aggregate write” names a conceptual consistency boundary, **not a database table or field**.
- State names are proposed domain vocabulary, **not an approved persistence contract**.
- `Critical = Yes` means ambiguity can affect money, inventory, authorization, irreversible actions, or data integrity.
- Configurable durations, limits, thresholds, tax policies, and provider choices must come from approved configuration; none may be hard-coded.
- All server-side writes require authenticated actor context where applicable, authorization, validation, transaction boundaries, and an audit correlation ID.
